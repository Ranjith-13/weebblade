# WeebBlade - System & Architecture Overview

**WeebBlade** is an automated, multi-source seasonal anime intelligence platform powered by an end-to-end data engineering pipeline. It collects, validates, reconciles, and enriches anime broadcast schedules, rating distributions, and studio catalogues across disparate upstream providers into a unified analytical data warehouse.

---

## 1. Executive Summary

Upstream anime information is fragmented across multiple independent platforms. Different providers maintain conflicting entity schemas, disparate rating scales, incompatible identifier namespaces, and differing seasonal classifications. 

WeebBlade addresses this fragmentation by executing scheduled collection and reconciliation workflows. Raw multi-source data is ingested via independent workers, transformed into validated Parquet snapshots, reconciled using PySpark schema consolidation, and exposed through an embedded DuckDB analytical database. A containerized FastAPI service and Next.js edge application consume the warehouse to deliver:
- **Seasonal Catalog Exploration:** Full multi-format filtering (TV, ONA, Movie, Special), studio lineage tracking, and genre indexing.
- **Broadcast Schedules & Countdown Clocks:** Real-time episode countdowns and Japan Standard Time (JST) weekly calendar matrices synchronized with client browser timezones.
- **Semantic Discovery:** Dense vector similarity search powered by local ONNX embeddings (`all-MiniLM-L6-v2`) over titles, genres, and synopses.
- **AI Trend Digest:** Automated seasonal trend summaries generated by Groq LLMs grounded directly in warehouse aggregation queries.
- **Public Analytical API:** Programmatic endpoints for querying catalogue snapshots, rating evolution, and airing schedules.

---

## 2. Problem Statement & Domain Complexity

Building a unified seasonal anime service introduces several core data engineering challenges:

| Challenge | Real-World Upstream Condition | Architectural Solution |
| :--- | :--- | :--- |
| **Namespace Fragmentation** | AniList, MyAnimeList (MAL), and Kitsu use independent numeric identifiers with no shared primary key. | Stable entity resolution graph (`processing/identity.py` and `bridge.py`) that maps cross-source identifiers into durable WeebBlade IDs (`wb_id`). |
| **Rating Discrepancies** | Kitsu uses 0–100 floats; MAL uses 1.0–10.0 decimals; AniList uses percentage integers. Unscored titles represent over 50% of off-season catalogues. | Normalization to a consistent warehouse standard with explicit source attribution and a dedicated UI "certainty" system (halftone shading for unscored titles). |
| **Schedule Instability** | Providers announce initial broadcast windows that frequently slip or delay. Broadcast slots late at night in Tokyo (e.g. Monday 00:30 JST) cross international calendar days. | Daily AniList episode delta extraction, separate airing status overrides, and explicit Tokyo calendar day partitioning. |
| **Provider Downtime** | Third-party public APIs experience outages or rate limiting (e.g. Jikan deprecation in October 2026). | Isolated, decoupled ingestion tasks per source. A failure in one provider never halts pipeline execution or corrupts existing snapshots. |

## 4. Pipeline Mechanics & Storage Strategy

### A. Ingestion & Precedence-Based Field Merging
Ingestion runs on a decoupled task architecture. Rather than performing a simplistic row union, consolidation implements a **field-level precedence hierarchy**:
1. **Metadata & Studio Authority:** MyAnimeList supplies studios, source material, and primary relations.
2. **Media & Artwork Enhancement:** AniList supplies banners, airing dates, episode countdowns, and trailer IDs.
3. **Fallback & Baseline Discovery:** Kitsu supplies synopsis baselines, localized titles, and supplementary stream links.

If a higher-priority provider omits a field (or fails during a scheduled run), the pipeline falls back to secondary sources without failing the run or introducing null holes.

### B. Analytical Warehouse (DuckDB & Parquet)
- **Immutable Historical Snapshots:** Processed records are persisted as partitioned Parquet files by run date, enabling point-in-time auditing and historical replay.
- **Materialized Serving Warehouse:** Weekly runs build a self-contained DuckDB warehouse (`warehouse.duckdb`) containing the reconciled catalogue, vector embeddings, and franchise relations.
- **Zero-Storage Serving:** The API downloads the materialized warehouse on boot, serving queries in-memory from container local storage without external database overhead.

### C. Semantic Search & Vector Embeddings
- Search queries are mapped to 384-dimensional dense vectors using an ONNX-runtime port of `all-MiniLM-L6-v2`.
- Running via ONNX reduces process resident memory from ~868 MB (PyTorch) to ~406 MB, allowing full semantic vector similarity search within constrained 512 MB memory environments.

## 5. Infrastructure & Operational Architecture

The platform operates on a resilient, zero-cost serverless architecture:

| Component | Host / Runtime | Operational Profile |
| :--- | :--- | :--- |
| **Pipeline Orchestrator** | GitHub Actions | Daily run (06:00 UTC) extracts airing schedules and score shifts; weekly run (Sunday) consolidates all 40 seasons. |
| **State & Checkpoints** | GitHub Release Assets | Pipeline state (`state.tar.gz`) is versioned and published as release assets across workflow runs. |
| **Off-Site Redundancy** | GitLab Package Registry | Checksummed copies of state archives are mirrored off-site (`MIRROR.md`), eliminating single-vendor dependency. |
| **Backend API** | Render Container | Dockerized FastAPI instance with memory bounds (192 MB buffer pool, 2 threads) and automated health checks. |
| **Edge Frontend** | Vercel Edge Network | Next.js 16 with cache boundaries (`use cache` + `cacheLife`), preventing duplicate upstream API load. |

## 6. Verification & Quality Assurance

The system is supported by over 45 comprehensive test suites covering:
- **Ingestion Resiliency:** Mocked upstream failure modes, rate limit responses, and schema variations.
- **Entity Resolution:** Cross-source identifier alignment and transliteration matching.
- **Scoring & Purity:** Reconciled score bounds, floating-point rounding precision, and timestamp alignment.
- **Frontend E2E Smoke Tests:** Playwright suites verifying WCAG contrast compliance, client-server hydration parity, zero layout shift (CLS = 0), and keyboard accessibility.

## 7. Roadmap & Current Scope

### Active Production Scope
- 40 historical and upcoming anime seasons (Fall 2017 to Winter 2027) actively tracked.
- Daily score velocity tracking and change detection.
- Automated weekly seasonal digest synthesis.

### Architectural Boundaries & Deferred Scope
- **Pre-2017 Historical Backfill:** Paused deliberately to maintain pipeline execution under GitHub Actions' 60-minute runner ceiling and preserve Render's 512 MB memory budget.
- **User Authentication / Personal Lists:** Intentionally out of scope; the application is architected as an open analytical reference service rather than a social logging tool.
